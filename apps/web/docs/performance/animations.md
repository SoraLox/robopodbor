# Производительность анимаций и 3D-симуляции

Заготовка под следующую итерацию оптимизации: инструменты замера, текущие
находки и план. Цель — сохранить все плавные анимации, убрав из них работу,
которая заставляет браузер пересчитывать вёрстку или перерисовывать большие
области на каждом кадре.

## Инструменты

### Профилировщик кадров (`src/lib/perf/frameProfiler.ts`)

Включается только по флагу, в обычном режиме — пустышка без накладных расходов:

- `?perf=1` в адресе (для HashRouter — до `#`: `/?perf=1#/calculate/...`);
- или `localStorage.perf = '1'` в консоли.

```ts
const profiler = createFrameProfiler('myAnimation', () => ({ items: list.length }));

function tick(ts: number) {
  profiler.frameStart(ts);
  profiler.time('step', () => update());
  if (visible) profiler.time('render', () => draw());
  else profiler.skipRender();
  profiler.frameEnd();
  requestAnimationFrame(tick);
}
```

В консоли: `__perf.myAnimation.snapshot()` — fps, avg/p50/p95/max по каждой
метрике и интервалу между кадрами, число кадров дольше 16.7 и 50 мс,
пропущенные отрисовки и значения из `extra`. `__perf.myAnimation.reset()` —
начать окно заново. Буфер — последние 600 кадров.

Симуляция склада уже подключена под именем `warehouse` (extra: draw calls,
треугольники, геометрии, текстуры, pixelRatio, размер drawing buffer, видна ли
сцена).

### Адаптивное разрешение (`src/lib/perf/adaptivePixelRatio.ts`)

Страховка для слабых машин: по p90 интервала rAF за 90 кадров снижает DPR
шагом 0.25 (от DPR устройства, но не выше 2, до 1.5) — только если три окна
подряд медленнее ~25 fps и после 180 кадров прогрева. Раньше хватало одного
окна медленнее 45 fps и пол был 1: качество падало при загрузке страницы или
на обычном ноутбуке, и сцена на сайте мылилась по сравнению с оригиналом. Обратно не поднимает —
смена DPR пересоздаёт drawing buffer и даёт фриз до ~1 с, контроллер с
возвратом качался бы между ступенями. Подключение — две строки в цикле:
`onRenderedFrame(ts)` после отрисовки и `onSkippedFrame()`, если кадр не рисовали.

### Бенчмарк симуляции (`scripts/perf/sim-bench.js`)

Открыть `/?perf=1#/calculate/warehouse/results/demo`, вставить файл в консоль.
Для каждого типа робота меряет три режима по 6 с: сцена работает, на паузе,
прокручена за экран. Результат — в `window.__simBench`.

Сравнивать замеры можно только на одном размере окна: размер canvas
определяет почти всю стоимость кадра. В DevTools — Device Toolbar с
фиксированным 1920×1080, DPR 2.

### Хуки для скриптов

`exposeForPerf(name, value)` кладёт объект в `window.__perfHooks` (только при
включённом флаге). Сейчас там `wizard` — zustand-стор мастера, через него
бенчмарк переключает решение без кликов по UI.

## Что уже сделано в симуляции

- Сцена не рисуется, когда она за пределами экрана (IntersectionObserver),
  на паузе и после остановки камеры. Логика шага при этом продолжает работать
  (стоит ~0.05 мс).
- Любой рендер React-компонента сцены выставляет `needsRender`, так что
  смена параметров на паузе сразу видна.
- Адаптивный DPR вместо фиксированного `min(dpr, 2)`.
- `.glb` сжаты meshopt + webp-текстуры, общий `GLTFLoader` с `MeshoptDecoder`.
  Исходники — в `assets-src/models/`, сборка — `scripts/build-models.sh`.
  Текстуры 2048 px, webp q92: при 1024 px и сильном сжатии модели мылились.
- Подписи размеров чанков на полу убраны: слой был холстом 2048×2048, который
  перерисовывался и заново грузился в GPU посреди каждого поворота камеры —
  рывок на 45°-повороте.

## Находки аудита и план

Порядок — по ожидаемому выигрышу.

### 1. Размытие (`backdrop-blur`) поверх WebGL — высокий приоритет

`src/upstream/simulation/WarehouseScene.jsx`: пять панелей с `backdrop-blur`
над канвасом. Пока сцена анимируется, композитор пересчитывает размытие
под каждой панелью на каждом кадре — это GPU-работа, которую не видно в
замере `render()`, но видно в интервале кадра. A/B-замер (отключение
`backdrop-filter`) на шумной машине дал неоднозначный результат, поэтому
перед решением повторить на реальном железе.

Варианты без потери вида:
- полупрозрачный фон без размытия (`bg-white/80`) — визуально близко на
  тёмной сцене;
- размытие только пока сцена на паузе/не анимируется (класс по состоянию);
- уменьшить площадь размытых панелей.

### 2. Draw calls у погрузчиков — высокий приоритет

185–490 draw calls в зависимости от момента (паллеты, коробки, стеллажи
создаются отдельными мешами). Одинаковые объекты — в `THREE.InstancedMesh`
(коробки груза, стеллажи, паллеты): десятки вызовов вместо сотен. Для
статичной части склада — `BufferGeometryUtils.mergeGeometries` по материалу.

### 3. Тени — средний приоритет

`sceneSetup.js`: VSM, карта 2048×2048, `castShadow` почти у всех объектов.
- Обновлять карту теней не каждый кадр: `renderer.shadowMap.autoUpdate = false`
  и `needsUpdate = true` раз в 2–3 кадра или только при движении роботов —
  тени на изометрии визуально не меняются.
- Снять `castShadow` с мелких деталей (рельсы, лента, клешня руки).
- 1024 вместо 2048 при DPR ≤ 1.25 (связать с адаптивным разрешением).

### 4. CSS-переходы по свойствам вёрстки

Мастер расчёта (выбор объекта → форма → роботы → расчёт) — сделано:

- `WizardCard`: смена ширины 380 ↔ 900 — FLIP на `transform`. Фон из трёх
  частей (края сдвигаются, середина `scaleX`), шапка едет вместе с краями.
- Пара «карточка + превью» центрируется `translateX` группы, превью вне потока.
- Погасшие шаги мастера — `content-visibility: hidden` (`WizardPane`):
  было ~1000 объектов вёрстки на каждом кадре анимации, стало ~100.
- `CalculatingStep`: прогресс — `scaleX` прямо в DOM, без setState на кадр.
- Картинки превью — кадры 800×450 в `public/pics/preview/` и заранее
  декодируются при входе на шаг: убран фриз 600 мс (CPU ×4) на первом открытии.
- Отклик на нажатие CTA — `active:scale-[0.98]` (transform).

Замер, CPU ×4: переход «Склад → Продолжить» — 4–6 пропущенных кадров → 0;
первое открытие превью — кадр 616 мс → 33 мс.

Осталось:

| Где | Что анимируется | Замена |
| --- | --- | --- |
| `WizardCard` → `WizardSubtitle` | `grid-template-rows` | дёшево после `content-visibility`, но при желании — FLIP `translateY` разделителя |
| `features/catalog/CatalogPreview.tsx` | `max-width` | как превью мастера: вне потока + `translateX` |

### 5. `transition-all` в `components/ui/button.tsx` — сделано

Свойства перечислены явно.

### 6. rAF-циклы вне симуляции — низкий приоритет

- `features/auth/components/RobotArmHero` (r3f): проверить `frameloop="demand"`
  или остановку, когда герой вне экрана / вкладка скрыта.

### 7. Скелетоны (`animate-pulse`) — низкий приоритет

Анимируют `opacity` — это дёшево. Проверить только, что их не десятки
одновременно на длинных списках (`ProjectsPage`, `CatalogPage`).

## Правила для новых анимаций

1. Анимировать только `transform` и `opacity` (и `filter` на небольших
   элементах). Никаких `width`, `height`, `top/left`, `margin`, `padding`,
   `grid-template-*` в `transition`/`@keyframes`.
2. `transition-all` не использовать — перечислять свойства.
3. `backdrop-filter` — только над статичным фоном. Над canvas, видео или
   анимацией — полупрозрачный фон.
4. Любой собственный rAF-цикл: останавливать, когда элемент вне экрана или
   вкладка скрыта; при `prefers-reduced-motion` — статичный кадр.
5. `will-change` ставить только на время анимации, не навсегда.
6. Новый rAF-цикл или WebGL-сцену сразу оборачивать в `createFrameProfiler`,
   чтобы её можно было замерить тем же способом.

## Как проверять изменение

1. Собрать прод-сборку (`npm run build && npx vite preview`) — dev-режим
   искажает замеры.
2. Зафиксировать окно (1920×1080, DPR 2), открыть с `?perf=1`.
3. Для симуляции — `sim-bench.js` до и после. Для CSS-анимаций — вкладка
   Performance в DevTools: доля Layout/Paint в кадрах анимации и Long
   Animation Frames (`PerformanceObserver({ type: 'long-animation-frame' })`).
4. Критерий: p95 интервала кадра ≤ 17.7 мс, ни одного кадра > 50 мс во
   время анимации, визуально без изменений.
