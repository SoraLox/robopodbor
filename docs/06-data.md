# 6. Загрузка и актуализация данных (ТЗ 6.6)

## Что загружается при первом запуске

Сервис `migrate` применяет миграции и запускает `apps/api/prisma/seed.ts`. Сид берёт данные из `apps/api/prisma/seed-data`:

| Файл | Содержимое |
|---|---|
| `object-types.json` | типы объектов: склад, аэропорт, медучреждение |
| `object-parameters.json` | поля паспортов с единицами, диапазонами, значениями по умолчанию и источниками. Значения по умолчанию взяты из демо-датасетов организатора |
| `robots-catalog/` | каталог роботов (v2): карточки по категориям, производители, коды, источники каждого значения (`sources.json`). Ведёт ответственный за каталог |
| `src/domain/catalogResearch.json` | характеристики из открытых источников (поиск через Perplexity 28.09.2026), каждое значение — со ссылкой на страницу. Принято только то, что автоматически сверено со страницей: число стоит на странице этой модели рядом с названием характеристики. Заполняет только пустые поля каталога, расхождения — в отчёт |
| `src/domain/catalogSupplements.json` | дополнения из материалов организатора: примеры решений по объектам, недостающие характеристики, решения вне каталога. Лежит в `src`, потому что нужен API и при загрузке версии из админки |
| `demo-calculation.json` | демонстрационный результат расчёта |

Каталог для сида собирает скрипт `prisma/seed-data/build-catalog.ts` (запуск из `apps/api`: `npx tsx prisma/seed-data/build-catalog.ts [папка]`) в `src/domain/catalogSolutions.json`. Тот же файл использует демо-режим сайта. Правила сборки — `src/domain/robotCatalog.ts`, общие для скрипта, сида и загрузки из админки.

Сид применяет каталог так же, как загрузка новой версии: новые решения добавляются, характеристики обновляются из каталога, поля, правленные администратором, остаются как есть (`src/catalogSync.ts`).

Источники данных по умолчанию описаны в `apps/api/src/domain/sources.ts`.

Сид можно запускать повторно: он обновляет структуру полей (подпись, единицу, раздел, тип, варианты) и добавляет недостающие записи. Правки администратора он не перезаписывает: обязательность, значение по умолчанию, диапазон и источник норматива, отредактированные решения и источники остаются как есть.

## Каталог решений

### Новая версия каталога роботов (3.3.2, 3.3.6)

Ответственный за каталог присылает папку каталога (структура v2: `index.json`, `categories.json`, `vendors.json`, `codes.json`, `sources.json`, `data/*.json`).

1. «Справочники» → «Каталог решений» → панель «Каталог роботов» → «Загрузить новую версию» → выберите папку. Отправляются только JSON-файлы; `schema/` и README не нужны.
2. Сервер собирает каталог по тем же правилам, что и при первом запуске, с дополнениями организатора, и показывает отчёт без записи: сколько решений добавится, изменится (по каким полям), останется без изменений; какие решения из базы в новой версии отсутствуют; в каких сохранятся правки администратора; расхождения каталога с организатором; число решений по основаниям применимости для каждого объекта.
3. «Применить версию» — запись одной транзакцией, событие в журнале изменений и новая версия данных.

Правила применения:
- характеристики и происхождение берутся из новой версии; поля, правленные администратором, не меняются;
- решения, которых нет в новой версии, **не удаляются** — на них могут ссылаться проекты. Удалить их можно вручную;
- фото хранятся на сайте (`apps/web/public/robots_photo`), а не в каталоге: у знакомых решений фото сохраняются, новым их добавляют в редакторе.
- Структура другой главной версии (не 2.x) отклоняется с понятной ошибкой.

Через API: `POST /api/admin/robot-catalog` (multipart, поле `files` — по файлу на поле, имя с путём внутри папки), `?dryRun=1` — только отчёт.

### Таблица организатора (3.3.2)

1. «Справочники» → «Каталог решений» → «Выгрузить xlsx». Получится таблица с актуальными колонками. Названия колонок совпадают с полями карточки: «Наименование», «Производитель», «Тип решения», «Цена, млн ₽», «Грузоподъёмность, кг», «Мин. ширина прохода, м» и так далее.
2. Перенесите данные организатора в эту таблицу. Распознаются и распространённые синонимы колонок: «название», «модель», «вендор», «стоимость», «цена с НДС», «страна», «навигация».
3. «Загрузить xlsx / csv» — выберите файл.
   - Строка с заполненным «ID» обновляет это решение.
   - Строка без «ID» ищет решение по паре «наименование + производитель». Если находит — обновляет, если нет — создаёт новое.
   - Строки с ошибками не сохраняются. После импорта показывается, сколько решений добавлено и обновлено, и список ошибок с номерами строк и причинами.
4. Импорт записывается в журнал изменений и меняет версию данных.

Через API: `POST /api/catalog/solutions/import` (multipart, поле `file`) и `GET /api/catalog/solutions/export?format=xlsx|csv`.

### Дополнение из открытых источников (3.3.3, 3.3.4)

Происхождение ведётся **по каждой характеристике** (`fieldSources` в карточке решения). Генератор сворачивает факты `robots-catalog/sources.json` в поля карточки:

- источники значения — вид (материалы организатора, производитель, реселлер, СМИ, госреестр), название, ссылка, дата публикации или обращения;
- `confirmed` — значение в источнике точное. `false` — «около», значение серии, пересчёт или вывод; примечание каталога («паллет в час на зону, не на робота») сохраняется в `note`;
- составное поле (габариты) точное, только если точна каждая составляющая.

Допущения команды (страна по производителю) и дополнения организатора получают свою запись. В карточке каталога у значения стоят сноски на нумерованный список источников со ссылками, неточные значения помечены «приблизительно», «допущение» или «изменено вручную» с примечанием. В сравнении — та же метка.

Правка администратора (форма или импорт таблицы) заменяет происхождение изменённых полей записью «правка администратора»: прежний источник подтверждал прежнее значение. Повторный сид обновляет происхождение из каталога, но не трогает поля, правленные администратором.

### Ручная правка (3.3.5, 3.3.6)

«Справочники» → «Каталог решений» → «Добавить позицию» или «Редактировать» в строке решения. Форма содержит все группы полей таблицы 3.3 и показывает полноту карточки. Каталог обновляется по запросу администратора — правкой или импортом. Изменения видны пользователям сразу.

## Паспорта объектов и нормативы

- «Справочники» → «Нормативы и значения по умолчанию»: для каждого поля задаются значение по умолчанию, минимум и максимум, источник и обязательность. Значение по умолчанию проверяется на попадание в диапазон.
- Новые поля и типы объектов добавляются в `object-parameters.json` и `object-types.json`, после чего сид перезапускается: `docker compose run --rm migrate`.

## Параметры объекта пользователя (3.2.3)

На шаге паспорта нажмите «Скачать шаблон Excel». В шаблоне колонки «ID поля», «Раздел», «Параметр», «Значение», «Ед. изм.», «Обязательное», «Допустимые значения», «По умолчанию», «Источник норматива», «Подсказка». Заполните колонку «Значение» и загрузите файл кнопкой «Загрузить из Excel / CSV».

Строки сопоставляются по «ID поля» или по названию параметра. Для каждого значения проверяются тип, единица измерения, диапазон и допустимые варианты. После загрузки показывается, сколько полей распознано, какие строки пропущены и какие ошибки найдены, с указанием строки и способа исправления.

Через API: `GET /api/object-types/{slug}/parameters/template?format=xlsx|csv` и `POST /api/object-types/{slug}/parameters/import`.

## Версии данных

Каждая правка каталога, нормативов или источников пишется в журнал изменений: пользователь, время, что изменилось, значения до и после. Отметка последней правки — это текущая версия данных. Она сохраняется в каждом снимке расчёта, поэтому видно, на каких данных сделан расчёт.

## Резервное копирование

```bash
docker compose exec db pg_dump -U robopodbor robopodbor > backup.sql
docker compose exec -T db psql -U robopodbor robopodbor < backup.sql
```
