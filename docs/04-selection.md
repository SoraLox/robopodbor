# 4. Алгоритм подбора и ранжирования (ТЗ 6.4, 3.4)

Код — `apps/api/src/domain/selection.ts`, версия правил `selection-2026.09c`. Вызов — `POST /api/selection` с телом `{ objectType, parameters }`. Тот же модуль работает в интерфейсе, поэтому результат на сервере и в демо-режиме совпадает.

## Шаги

1. **Паспорт объекта.** Незаполненные поля берутся из значений по умолчанию паспорта. Поэтому подбор работает и в гостевом демо без ввода данных (ТЗ 2.1.1).
2. **Кандидаты.** В подбор попадают решения каталога, у которых в `objectTypes` есть выбранный тип объекта (3.4.1). Каталог — реальный каталог роботов (`apps/api/prisma/seed-data/robots-catalog`), его переводит в решения скрипт `build-catalog.ts`. Тип объекта попадает в `objectTypes` двумя путями, это записано в `objectFit`:
   - `declared` — объект указан в каталоге (поле `site`);
   - `example` — организатор приводит решение как пример для этого объекта («Примеры решений», `seed-data/catalog-supplements.json`); считается подтверждённым, как `declared`;
   - `inferred` — объект не указан, но сценарий применения и категория робота подходят объекту. Правила — `FIT_RULES` в `build-catalog.ts`, точечные исключения — `FIT_OVERRIDES`.

   Из того же файла дополнений генератор заполняет пустые характеристики каталога и добавляет решения, которых в каталоге нет (PuduBot 2 — `EX0001`). Заполненные значения каталога не перезаписываются: расхождения генератор печатает для ответственного за каталог.
3. **Проверки.** Каждое ограничение продукта сравнивается с параметром объекта. Итог проверки попадает в один из четырёх списков:
   - **причины соответствия** — ограничение проверено и выполняется;
   - **блокеры** — ограничение делает применение невозможным;
   - **ограничения** — применять можно, но есть условия;
   - **недостающие данные** — проверить нельзя.
4. **Статус.**
   - `excluded` («Не подходит») — есть хотя бы один блокер. Такое решение не рекомендуется, его балл равен 0 (3.4.3).
   - `needs-review` («Требует проверки») — блокеров нет, но хотя бы одну проверку «подходит / не подходит» выполнить не удалось, применимость к объекту выведена по сценариям (`inferred`), характеристики не подтверждены или решение ещё не в серийной эксплуатации (пилот, НИОКР).
   - `recommended` («Рекомендовано») — все проверки выполнены, решение в эксплуатации.
5. **Сортировка.** Сначала рекомендованные, затем требующие проверки, затем исключённые. Внутри группы — по баллу.

## Проверки

| Проверка | Параметр объекта | Характеристика решения | Блокер, если |
|---|---|---|---|
| Тип объекта | выбранный тип | `objectTypes` | тип не поддерживается |
| Грузоподъёмность | масса паллеты или штучной единицы (склад), масса багажа (аэропорт), масса тележки с питанием — только для процесса «белье и питание» (медучреждение) | `payloadKg` | грузоподъёмность меньше массы. Складской мобильный робот, который не берёт паллету, но берёт штучный груз, не исключается — получает ограничение «только лёгкий груз» |
| Ширина прохода (мобильные решения) | ширина проходов (склад), ширина коридоров (медучреждение) | `minAisleWidthM` | проход уже требуемого |
| Ровность пола | ровность пола, мм на 2 м | `maxFloorDeviationMm` | пол хуже допуска |
| Высота помещения | высота потолков в зоне хранения | `minCeilingHeightM` | потолки ниже |
| Температура (аэропорт, уличные решения) | температура в неотапливаемых зонах | `minTempC` | объект холоднее нижней рабочей температуры |
| Допуск на перрон (аэропорт) | требуемая сертификация | `airsideCertified` | допуска нет |
| Этажность (медучреждение, мобильные решения) | число этажей, лифты с API, пандусы | `elevatorIntegration` | этажей больше одного, интеграции с лифтами нет и пандусов нет |
| Бюджет | планируемый бюджет на роботизацию | цена единицы | цена одной единицы выше бюджета |

Ограничения без исключения:

- шум выше нормы для зоны;
- у объекта нет WMS, а роботам она нужна;
- нужна интеграция со СКУД;
- лифты без API;
- ограничения из карточки решения.

Недостающие данные, при которых решение получает статус «Требует проверки»:

- для проверки нет характеристики в карточке решения (например, ширины прохода);
- параметр не заполнен в паспорте объекта;
- производитель не указывал этот тип объекта — применимость выведена по сценариям;
- решение на стадии НИОКР;
- характеристики не подтверждены поставщиком.

Показываются, но статус не понижают:

- незаполненные обязательные поля карточки — в реальном каталоге заполнена малая часть полей, и иначе «Требует проверки» получили бы все решения;
- допущения по полям карточки (например, страна происхождения взята по стране производителя).

## Балл ранжирования (3.4.5)

Балл — сумма пяти критериев, максимум 100. В карточке решения показан вклад каждого критерия в виде «набрано / максимум».

| Критерий | Максимум | Расчёт |
|---|---|---|
| Зрелость решения | 30 | эксплуатация — 30, пилот — 18, НИОКР — 6 |
| Соответствие объекту | 25 | 25 − 5 × число ограничений, не меньше 10 |
| Цена относительно бюджета | 20 | 20 × (1 − цена единицы / бюджет), в пределах 0…20; без бюджета — 10 |
| Полнота и подтверждённость данных | 15 | 15 × полнота карточки × (1, если данные подтверждены, иначе 0,7) |
| Российский производитель | 10 | Россия — 10, иначе 4 |

Веса — экспертное допущение команды. Они собраны в одном месте кода и меняются вместе с версией правил.

## Ручное добавление (3.4.4)

Пользователь может выбрать исключённое решение вручную: на шаге процессов и в сравнении появляется предупреждение с причиной исключения. Выбор сохраняется, расчёт выполняется.
